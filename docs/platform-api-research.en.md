# OmniSocial — Platform API Research

Research pass on the 8 target platforms for a single-user, publish-once/post-everywhere dashboard running on a $0 budget (Vercel Hobby + Vercel Postgres + Vercel Blob). LinkedIn is intentionally excluded.

**Methodology note / limitation:** The sandbox's network egress proxy blocks direct fetches to `core.telegram.org`, `discord.com`, `developers.facebook.com`, `docs.bsky.app`, and `docs.joinmastodon.org` (whole-domain blocks), so official pages could not be fetched directly in every case. Where that happened, findings below come from web search results that quote or closely paraphrase the official docs (search snippets), from the official GitHub source repos (`discord/discord-api-docs`, `mastodon/documentation`) fetched via raw GitHub content (not blocked), or from Reddit/Bluesky pages that were reachable. Every fact below is attributed to its source; anywhere the underlying official text could not be directly verified, that is called out explicitly rather than presented as confirmed.

## Telegram — Bot API

- **Official docs:** https://core.telegram.org/bots/api (could not be fetched directly due to egress block; findings below are from search-engine snippets referencing this page, plus https://core.telegram.org/bots/faq).
- **Auth method:** Bot token. Setup: message `@BotFather` on Telegram, run `/newbot`, follow the prompts (bot name + username), and BotFather returns a token string (`123456:ABC-DEF...`). That's the entire credential — no OAuth flow, no app review.
- **Approval/review process:** None. Any bot token works immediately in production. The only gate is Telegram's anti-spam/flood system, which is automatic and reactive, not a review process.
- **Publish endpoint(s):** `sendMessage` for text; `sendPhoto` for an image (with an optional `caption` for text) — the photo is uploaded as `multipart/form-data`, or passed as a URL/file_id. A "title + text + image" post maps cleanly to a single `sendPhoto` call with a caption; if there's no image, just `sendMessage`. Bots post into a chat/channel/group they've been added to (with posting rights for channels).
- **Delete endpoint:** `deleteMessage(chat_id, message_id)`. Per widely-cited documentation summaries, a bot can only delete messages it sent itself, and only within a limited time window (commonly cited as 48 hours) in most chat types; in channels/supergroups where the bot is admin, restrictions can be looser. This should be verified against the live API docs before relying on it for "always deletable" behavior in the dashboard.
- **Metrics/stats endpoint:** Very limited for a bot. There is no generic "likes" concept in Telegram. Channel post view counts are visible in Telegram client UIs but are not reliably exposed through a simple Bot API call; reactions on messages exist as a feature but bot-level read access to aggregate reaction counts is not confirmed here — treat Telegram as effectively "no meaningful engagement stats via Bot API" for this project.
- **Rate limits:** Roughly 1 message/second to the same chat (bursts tolerated), ~30 messages/second in aggregate for bulk sends, and ~20 messages/minute into the same group. Exceeding limits gets a `429` with a `retry_after`. A paid "Telegram Stars" broadcast tier can raise the aggregate limit to ~1000 msg/sec at ~0.1 Stars per message beyond the free 30/sec — irrelevant at single-user dashboard scale.
- **Cost:** Free. No paid tier is needed for this use case.
- **Key gotchas:** Posting to a **channel** requires the bot to be added as an admin of that channel (not just "a chat"); posting into a normal group is simpler. Because delete rights and windows are message-type/chat-type dependent, this is the platform most likely to silently fail on "delete" for older posts — build in a fallback (e.g., show "could not delete, may be too old" rather than assuming success).

## Discord — Bot API / Webhooks

- **Official docs:** https://discord.com/developers/docs/resources/message and https://discord.com/developers/docs/topics/rate-limits (direct fetch blocked; content below verified via the official docs' own GitHub source at `discord/discord-api-docs`, path `developers/resources/message.mdx` and `developers/topics/rate-limits.mdx`, fetched via `raw.githubusercontent.com`).
- **Auth method:** Bot token, created in the **Discord Developer Portal** (discord.com/developers/applications): create an application → add a **Bot** → copy the token → generate an OAuth2 invite URL with the `bot` scope and permissions **Send Messages**, **Attach Files**, **Manage Messages** (needed to delete), then use that URL to add the bot to your own server/channel. Alternative for even simpler one-way posting: a **Channel Webhook** (created in a channel's Integrations settings) gives a URL you can POST to directly with no bot/OAuth setup at all — but a webhook alone can't delete or read reactions as flexibly as a bot can, so a bot token is the better fit here.
- **Approval/review process:** None for a bot used only in your own server(s). Discord's "Verification" and "unusual growth" gates only kick in once a bot is added to 75+ guilds — irrelevant for a single-user dashboard posting into your own server/channel.
- **Publish endpoint(s):** `POST /channels/{channel.id}/messages`. Text goes in the `content` field; an image is attached as `multipart/form-data` using a `files[n]` part plus a `payload_json` part describing the message and attachment metadata (the attachment's `id` must match its file index `n`).
- **Delete endpoint:** `DELETE /channels/{channel.id}/messages/{message.id}`, requires the bot to have `MANAGE_MESSAGES` (own messages can be deleted without that permission in some contexts, but granting it avoids edge cases). Per the rate-limits doc, delete-message calls are bucketed with a more generous/faster limit specifically so moderation-style bulk deletes work well.
- **Metrics/stats endpoint:** Discord has no "likes/shares" concept. The closest equivalent is **reactions** — `GET /channels/{channel.id}/messages/{message.id}/reactions/{emoji}` lists users who reacted with a given emoji, and the message object includes a `reactions` array with counts per emoji. There is no native "comment count" either (replies are just messages in the channel).
- **Rate limits:** Global cap of 50 requests/second per bot; individual routes have their own (often shared/bucketed) limits communicated via `X-RateLimit-*` response headers — the docs explicitly say not to hard-code limits and to read the headers. IP-level protection kicks in at 10,000 invalid (401/403/429) requests per 10 minutes.
- **Cost:** Free. No paid tier needed.
- **Key gotchas:** File size caps apply (8MB for non-boosted servers, higher for boosted ones) — relevant if the "optional image" is large. Because Discord has no page/profile concept, "posting to Discord" really means posting into a specific channel of a specific server you already control — the dashboard needs a channel ID (and bot must already be invited there).

## Facebook Page — Meta Graph API

- **Official docs:** https://developers.facebook.com/docs/pages/publishing and https://developers.facebook.com/docs/permissions (domain fetch blocked by egress proxy in this session; findings below come from search-engine snippets quoting these pages and closely-related Meta documentation pages such as `developers.facebook.com/documentation/pages-api`).
- **Auth method:** OAuth2, resulting in a long-lived **Page Access Token**. Setup: create a Meta developer account and a "Business" type app at developers.facebook.com, add the **Facebook Login**/Pages product, generate a User Access Token with Page permissions, then exchange it for a Page Access Token tied to your specific Page. Requires you to already administer the target Facebook Page.
- **Approval/review process:** **Yes.** Publishing needs `pages_manage_posts` (plus dependencies `pages_read_engagement`, `pages_show_list`) at **Advanced Access**, which requires (a) Meta **App Review** — a screencast-based submission per permission showing the exact use case, and (b) **Business Verification** of your legal business entity through Meta Business Manager (documents, domain verification, sometimes a phone call). Search-derived estimates: **App Review ~1–3 weeks per submission** (5–10 business days initial, faster on resubmission), with Business Verification running on its own separate timeline; end-to-end, budget **2–4+ weeks**, more if multiple permissions each need a resubmission round. **Important exception:** while your app only touches Pages that you (or accounts with a role on your app/Business) administer, you can use permissions at **Standard Access** without going through full review — this is exactly the single-user OmniSocial scenario, so review may be avoidable initially, but Meta's own guidance is that the moment you'd manage *any* Page not tied to your app's roles, full review is required. Confirm current Standard-vs-Advanced-Access thresholds directly in your Meta App Dashboard before relying on this.
- **Publish endpoint(s):** Text-only: `POST /{page-id}/feed` with `message`. With a photo: `POST /{page-id}/photos` with the image file and a `caption` (acts as the text). Requires the Page Access Token, not a user token.
- **Delete endpoint:** `DELETE /{post-id}` (with the Page Access Token) — supported.
- **Metrics/stats endpoint:** `GET /{post-id}/insights` for metrics like `post_impressions`, `post_impressions_organic`, `post_engaged_users`, `post_clicks`, and reaction breakdowns (`post_reactions_by_type_total`, `post_reactions_like_total`, etc. — requires `pages_read_engagement` + `read_insights`). Comment/share counts and lists are available via `/{post-id}/comments` and the post object's `shares` field.
- **Rate limits:** No single fixed public number found for Page publishing volume in this pass; Meta throttles per-app/per-user using a dynamic "Business Use Case" usage score exposed in response headers, rather than a flat requests/hour figure. At single-user, few-posts-per-day scale this is very unlikely to be a practical constraint.
- **Cost:** Free to use the Graph API itself; no paid tier required for posting/reading your own Page's data at this scale.
- **Key gotchas:** You must already own/administer a Facebook Page (a personal profile cannot be posted to via this API). Business Verification is the single biggest source of delay/friction across all three Meta-owned platforms in this project (Facebook, Instagram, Threads) — since all three permissions likely get requested from the same Meta app, it's worth planning one verification effort that unblocks all three at once rather than three separate ones.

## Instagram Business — Meta Graph API (Content Publishing)

- **Official docs:** https://developers.facebook.com/docs/instagram-platform/content-publishing and https://developers.facebook.com/docs/instagram-platform/reference/instagram-media/ (domain fetch blocked; findings from search snippets quoting these pages).
- **Auth method:** OAuth2 through the same Meta app used for Facebook, using **Instagram API with Facebook Login**. Requires: (1) an Instagram account converted to **Business or Creator** type, (2) that account linked to a Facebook Page you administer, (3) permissions requested/granted through that Page's token.
- **Approval/review process:** **Yes** — the same Meta App Review + Business Verification pipeline as Facebook (`instagram_business_basic`, `instagram_business_content_publish`, plus `instagram_manage_comments`/`instagram_manage_insights` if you want comment moderation or extended metrics). Search-derived estimate: standard permissions typically clear review in **roughly 2–4 weeks**. As with Facebook, Standard Access (testing only with your own app's roles) may not require full review for a single-user setup — verify current thresholds in your App Dashboard.
- **Publish endpoint(s):** Two-step "container" flow: (1) `POST /{ig-user-id}/media` with `image_url` (must be a publicly reachable URL — this is where Vercel Blob's public URL is useful) and `caption`, which returns a container ID; (2) `POST /{ig-user-id}/media_publish` with that container ID to actually publish. No direct "upload local file" — the image must already be hosted at a public URL when you create the container.
- **Delete endpoint:** **`DELETE /{ig-media-id}` is supported** — this directly contradicts the prior mockup's `directDelete: false` assumption for Instagram. Per the docs/search findings: supported for non-ad posts, stories, reels, and entire carousel albums; you cannot delete a single image out of a carousel — only the whole carousel container. Requires the `instagram_manage_comments`-adjacent content permission (specifically content-management scope); deletion is irreversible.
- **Metrics/stats endpoint:** `GET /{media-id}/insights` (impressions, reach, likes, comments, saves, etc., permission-gated by `instagram_manage_insights`).
- **Rate limits:** Publishing is capped at **25 API-published posts per rolling 24-hour window** per the most commonly cited figure (checkable live via `GET /{ig-user-id}/content_publishing_limit`) — note the window is a rolling 24h from each post's timestamp, not a calendar-day reset. Some more recent third-party sources claim higher current limits (50 or even 100); this could not be independently confirmed against the primary doc in this pass, so plan around 25/day as the conservative number and verify against your own app's `content_publishing_limit` response once you have API access.
- **Cost:** Free to use.
- **Key gotchas:** Personal Instagram accounts cannot be used at all — conversion to Business/Creator plus a linked Facebook Page is mandatory before any of this works. The image-must-be-a-public-URL requirement means your Vercel Blob upload has to be publicly readable (not just accessible to your app) at the moment Instagram's servers fetch it to build the container.

## Reddit — Official API (OAuth2)

- **Official docs:** https://www.reddit.com/dev/api (this specific URL could not be fetched directly in this session — tool reported it as unreachable — findings below come from search-engine results referencing Reddit's developer platform pages and the 2023 API pricing/terms changes).
- **Auth method:** OAuth2. Setup: log into Reddit, go to `reddit.com/prefs/apps`, click "create app," choose type **"script"** (correct for a single-user server-side integration — you get a `client_id`/`client_secret` directly tied to your own account, no separate user-authorization flow needed), set a redirect URI (e.g., `http://localhost:8080` works for script apps), and save. Every request must also send a descriptive `User-Agent` header in the form `platform:app_id:version (by /u/yourusername)` — Reddit is known to reject generic/default user agents.
- **Approval/review process:** **None** for the free/non-commercial hobby tier used here — script apps for personal use work immediately after creation. Reddit's 2023 pricing overhaul only affects **high-volume commercial** use, which requires a separate application, contract pricing, and its own review — not applicable at single-user dashboard scale, but worth being aware of if usage ever grows or if the tool is ever resold commercially at scale.
- **Publish endpoint(s):** `POST /api/submit` with `sr` (subreddit), `kind` (`self` for text, `link` for a URL, or an image-post kind), `title`, and body text or URL. Image posts to Reddit are handled either via a link post to an already-hosted image URL (simplest, and fits the "Vercel Blob public URL" pattern already used for Instagram) or via Reddit's own media upload/lease flow for native image posts — the link-post route is simpler to implement and avoids extra API surface.
- **Delete endpoint:** `POST /api/del` with the post's `id` (fullname, e.g., `t3_xxxxx`) — supported, for your own content only.
- **Metrics/stats endpoint:** Yes — fetching the post (e.g., via its listing or `/api/info`) returns `score`/`ups`, `downs` (largely obfuscated by Reddit's fuzzing), and `num_comments`.
- **Rate limits:** ~100 queries/minute (QPM) per OAuth client on the free/non-commercial tier, averaged over roughly a 10-minute window (bursts tolerated); ~10 QPM if not using OAuth at all (not applicable here since OAuth is mandatory anyway).
- **Cost:** Free for this use case (personal/non-commercial, low volume).
- **Key gotchas:** Reddit is the one platform in this set with genuine **community-level gatekeeping independent of the API**: individual subreddits commonly impose their own account-age (often referenced informally as a few days to weeks) and karma minimums, and Reddit's own spam systems throttle brand-new accounts regardless of API access. This means "which subreddit(s), and is the posting Reddit account already established" is a real prerequisite, not just an API technicality — an API key on a brand-new or low-karma account can still get posts auto-removed by subreddit AutoModerator rules that the Reddit API itself won't warn you about in advance.

## Bluesky — AT Protocol

- **Official docs:** https://docs.bsky.app/docs/get-started, https://docs.bsky.app/docs/tutorials/creating-a-post, https://docs.bsky.app/docs/advanced-guides/rate-limits, https://atproto.com/blog/create-post (domain fetch blocked in this session; findings below come from search-engine snippets closely quoting these official pages).
- **Auth method:** Two options. (1) **App Password** (legacy but still functional): generate one in Bluesky app Settings → App Passwords, then call `com.atproto.server.createSession` with your handle + app password to get session tokens — simplest path for a single-user server-side integration. (2) **OAuth**: the AT Protocol team's stated direction going forward and recommended for anything started fresh in 2026, but heavier to implement (dynamic client registration, DPoP-bound tokens) and arguably overkill for a single-account dashboard. For this project's scale, an app password is the pragmatic choice, with a note to revisit OAuth if/when app passwords are actually deprecated (no hard deprecation date found in this pass).
- **Approval/review process:** None. No app registration or review gate at all — the account's own credentials are the whole story.
- **Publish endpoint(s):** Two-step for an image post: (1) `com.atproto.repo.uploadBlob` — POST the raw image bytes with the correct `Content-Type`, get back a blob reference (hash, mime type, size); (2) `com.atproto.repo.createRecord` with `collection: app.bsky.feed.post`, embedding the blob reference under `embed.$type: app.bsky.embed.images`. Text-only posts skip step 1 and just create the record directly.
- **Delete endpoint:** `com.atproto.repo.deleteRecord` — supported, standard.
- **Metrics/stats endpoint:** Yes — post views returned by endpoints like `app.bsky.feed.getPostThread` / `getPosts` include `likeCount`, `repostCount`, and `replyCount` directly on the post view object.
- **Rate limits:** Points-based budget: **5,000 points/hour, 35,000 points/day** per account. Creating a record costs 3 points, updating 2, deleting 1 (same cost schedule applies to likes/reposts/follows). At single-user, a-few-posts-a-day scale this is far from a binding constraint (thousands of creates/day are within budget).
- **Cost:** Free.
- **Key gotchas:** Bluesky/AT Protocol is a genuinely open, still-evolving spec — expect more churn here than on the older platforms (e.g., the OAuth-vs-app-password transition). Images must be uploaded as blobs and referenced by hash/size/mime rather than a plain URL, which is a slightly different mental model than Instagram/Reddit's "point at a public URL" pattern.

## Threads — Threads API (Meta)

- **Official docs:** https://developers.facebook.com/docs/threads (overview), https://developers.facebook.com/docs/threads/posts/delete-posts/ (domain fetch blocked; findings from search snippets quoting these Meta pages).
- **Auth method:** OAuth2 via a Meta app configured with the **Threads API** product (a separate product from the classic Facebook/Instagram Graph API surface, even though it's the same Meta for Developers console). Requires a Threads account and Meta developer/business setup.
- **Approval/review process:** **Yes.** Per-permission Meta App Review (screencast-based, same model as Facebook/Instagram) is required for Advanced Access, and search results additionally describe a **tech-provider identity verification step (up to ~1 week)** as a prerequisite before Advanced Access permissions are usable at all, on top of the review itself (search-derived estimate: **2–4 weeks** per Meta's stated review process). As with the other two Meta platforms, Standard Access scoped to your own app's roles may avoid full review for single-user use — verify in your app dashboard.
- **Publish endpoint(s):** Same two-step container pattern as Instagram: `POST /{threads-user-id}/threads` (create container, with `text` and optionally `image_url`), then `POST /{threads-user-id}/threads_publish` (publish the container).
- **Delete endpoint:** **Supported as of March 6, 2025** — a `DELETE` call on the post ID, gated behind the `threads_delete` permission (which must be separately requested/enabled as its own "use case" in the Meta app, distinct from `threads_basic`/`threads_content_publish`). **This directly contradicts the prior mockup's `directDelete: false` assumption for Threads** — delete is now a real, documented capability, but it is its own permission that must be explicitly requested and reviewed, so it's an extra App Review item, not something that comes "for free" alongside publish permissions.
- **Metrics/stats endpoint:** `GET /{media-id}/insights`; publishing-quota usage checkable via `GET /{threads-user-id}/threads_publishing_limit`.
- **Rate limits:** **250 published posts / rolling 24h** (a carousel counts as one post); **100 deletions / rolling 24h**.
- **Cost:** Free to use.
- **Key gotchas:** Because `threads_delete` is a distinct, separately-reviewed permission from publishing permissions, plan for it explicitly in the App Review submission (with its own screencast demonstrating delete behavior) rather than assuming it's bundled with `threads_content_publish`.

## Mastodon — REST API

- **Official docs:** https://docs.joinmastodon.org/client/intro/, https://docs.joinmastodon.org/methods/statuses/, https://docs.joinmastodon.org/api/rate-limits/ (domain fetch blocked directly; content verified via the official docs' own GitHub source, `mastodon/documentation`, fetched via `raw.githubusercontent.com` — paths `content/en/client/token.md` and equivalent status/rate-limit pages).
- **Auth method:** OAuth2, registered **per instance** (this is the federation-specific part — there is no single global Mastodon app registry). Setup: `POST https://<your-instance>/api/v1/apps` with `client_name`, `redirect_uris` (use `urn:ietf:wg:oauth:2.0:oob` for manual/local flows), and `scopes` (e.g. `read write push`) → get back `client_id`/`client_secret`; then `POST /oauth/token` to obtain a bearer `access_token`. Verify with `GET /api/v1/apps/verify_credentials`.
- **Approval/review process:** None platform-wide — no Mastodon-the-protocol app review process exists. However, because Mastodon is federated, the **specific instance/server you register on can impose its own signup or app rules** (some instances require manual approval to even create an account, or restrict bot-like posting) — this is a per-instance policy question, not an API technicality.
- **Publish endpoint(s):** Image first: `POST /api/v1/media` with the file, returns a media attachment ID (may need a brief poll if the instance processes it asynchronously); then `POST /api/v1/statuses` with `status` (text) and `media_ids[]` referencing the uploaded attachment(s). Requires `write:statuses` scope (and `write:media` for the upload step).
- **Delete endpoint:** `DELETE /api/v1/statuses/:id` — supported; response includes enough of the original content/media info to support "delete and redraft" UX if wanted; an optional `delete_media` query param can also purge the attached media immediately.
- **Metrics/stats endpoint:** Yes, directly on the Status object returned by any read: `replies_count`, `reblogs_count`, `favourites_count`. Detailed lists of who reacted are available via `/api/v1/statuses/:id/favourited_by` and `/reblogged_by`.
- **Rate limits:** Documented **default** is 300 requests / 5-minute window per app/token, plus a broader 7,500 requests / 5 min per-IP ceiling — but because Mastodon is federated software, **each instance admin can change these defaults**, so the numbers only hold for whichever instance you actually target.
- **Cost:** Free — the API itself has no paid tier; the only cost consideration is whether your chosen instance is free to join or (for self-hosting your own instance) infrastructure cost, which is outside this API-focused scope.
- **Key gotchas:** "Mastodon" isn't one service — it's thousands of independently-run instances/servers running compatible software, so **which instance you register the OmniSocial account/app on is itself a decision** (e.g. mastodon.social vs. a smaller or self-hosted instance), and behavior (rate limits, signup rules, moderation policy, even API version/feature availability) can vary slightly instance to instance. Pick one specific instance for this integration and treat its docs/behavior as authoritative for your deployment.
